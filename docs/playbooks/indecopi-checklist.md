# INDECOPI accreditation checklist (Guía v4.0)

What an accreditation of signature software by INDECOPI (IOFE, Peru, Ley 27269) asks, item by item, and what shows
each item with SimpleSign. It is the input of the INDECOPI playbook (`indecopi-guia-v4.json`, generated by
`tools/playbooks/indecopi.py`): every item with **P** has at least one step tagged with its id (`F-5`, `V-12`…), which
`PlaybookValidatorTests.IndecopiSample_CoversEveryChecklistItemARunCanShow` checks.

Source: INDECOPI, *Guía de Acreditación de Aplicaciones de Software* — "Requerimientos para acreditar una aplicación
(SW) de Clave Pública (PK)", version 4.0 (2016, Res. 010-2016/CFE-INDECOPI), published at
<https://www.gob.pe/institucion/indecopi/informes-publicaciones/5449761-guia-de-acreditacion-de-aplicaciones-de-software-de-firma-digital-sfd>.
Its annex B is the checklist the applicant fills in; each section numbers its items from 1. The ids here are that
numbering:

| Ids | Section of the guide | Requirements (body) |
|---|---|---|
| **F-1 … F-32** | 4.2 Signing by automated agents (unattended, one key, the organization's cryptographic module in scope) | Req. 11–20 |
| **V-1 … V-32** | 4.3 Verification by automated agents | Req. 21–30 |
| **S-1 … S-4** | 4.4 Time-stamp requests (optional; can be added to any type) | "Req. 31" in annex B |
| **E-1 … E-19** | 4.1 End-user signing software (the user's token and the servers are out of scope) | Req. 1–10 |

The item texts below are short paraphrases; the guide's wording rules. Every requirement is mandatory, except the
trusted-list block (items 1–4) which is evaluated only when the applicant asks for it; many items are conditional ("if
the application…"), and the applicant justifies in annex B each item it says does not apply.

**How**, for each item:

- **P** — a step of the `indecopi-guia-v4` playbook shows it: a signature or a validation against the Sandbox (its
  trusted list `/tl/tl.xml`, read with the IOFE profile, for the trusted-list items), through the library and the CLI, kept as evidence;
- **U** — covered by unit or integration tests of the library, not by a run;
- **N** — needs something new first;
- **X** — outside the library: the accredited product, its operation or its documentation must show it (the column
  says what SimpleSign offers towards it).

## 4.2 Signing by automated agents (F)

| # | What the guide asks | How |
|---|---|---|
| F-1 | Trusted list: verify INDECOPI's signature on the TSL and that it chains to INDECOPI's root | P (`tsl-ok`, `tsl-wrong-signer`, `tsl-tampered`) + U (`IofeRealListTests`: the real list verifies with the TSL Suscriptor certificate, another key is refused). The signer certificate is given out of band (`IofeExtensionOptions.TrustedListSigners`); its chain to INDECOPI AAC RAIZ is for the deployment to confirm |
| F-2 | Trusted list: it has not expired | P (`tsl-expired`) + U (`IofeTrustedListSourceTests.Anchors_AfterNextUpdate_AreNoneUntilAGoodCopyIsRead`) |
| F-3 | Trusted list: the signer's root CA is listed in it | P (`tsl-ok`, `tsl-tsa-unspecified`) |
| F-4 | Trusted list: it can be downloaded again periodically, according to its validity | U (`IofeTrustedListSourceTests`: refresh on demand and on a schedule, atomic swap, last good copy kept until NextUpdate, rollback refused) — `IofeTrustedListSource`, `AddSimpleSignIofe(options, interval)` |
| F-5 | Revocation: fetch the CRL over HTTP, LDAP or HTTPS | P (`crl-https-good`, `crl-https-revoked`, `crl-ldap-good`, `crl-ldap-revoked`; HTTP in every other signing step) |
| F-6 | Revocation: the CRL is signed by the CA entitled to issue it | P (`crl-wrong-key`) |
| F-7 | Revocation: the CRL is current | P (`crl-expired`, `crl-no-next-update`) |
| F-8 | Revocation: the CRL is checked before signing, so a revoked certificate never signs | P (`crl-https-revoked`, `crl-stale`, `crl-down`) |
| F-9 | Revocation: every certificate of the chain is not revoked | P (`chain-revoked`) |
| F-10 | Revocation: or OCSP (RFC 2560) for the certificate and its chain | P (`ocsp-good`, `ocsp-revoked`, `ocsp-unauthorized`) |
| F-11 | An expired certificate cannot sign | P (`expired`, `not-yet-valid`, `chain-expired`) |
| F-12 | The certificate's nonRepudiation bit is checked | P (`no-nonrepudiation-agent` with `IofePolicies.SigningNonRepudiation`; `no-key-usage`, `no-key-usage-extension`, `no-key-usage-cades`, `no-key-usage-xades`). `IofePolicies.Signing` also accepts digitalSignature (section 4.1): an automated agent uses `SigningNonRepudiation` |
| F-13 | The application is protected against unauthorized access | X — the product (authentication, network exposure). The Agent listens on 127.0.0.1 only; the TestBench and Sandbox are test tools |
| F-14 | The certificate checks cannot be switched off (except under a contingency procedure INDECOPI approved) | X — the product must not expose a way to relax the policy. In the library the checks are the `SigningPolicy` given to the signer; relaxing one is an explicit `.With(…, IGNORE)` in code or a policy file, recorded in the audit trail (`policy` of each record) |
| F-15 | Audit log of the signatures produced, by kind of transaction | P (`audit`, `audit-refused`) + U (`JsonLinesAuditSink` hash chain, `simplesign audit verify`) |
| F-16 | Administrator rights cannot produce signatures outside the defined transaction | X — the product's roles and key access |
| F-17 | The private key signs only inside the certified cryptographic module, never in the application's libraries | X — the deployment's HSM or token. SimpleSign signs through `IExternalSigner` (PKCS#11 `SimpleSign.Signers.Pkcs11`, CSC, deferred signing) and never needs the key |
| F-18 | No automatic copies of the private key on the computer | X — as F-17; the library never exports or stores a key |
| F-19 | A module that is part of the solution is FIPS 140-2 or Common Criteria EAL 4+ | X — the HSM or token chosen |
| F-20 | (Key in the solution) two-person control of access to the key from its generation | X — key ceremony |
| F-21 | (Key in the solution) two-person control of the key's copies | X — key ceremony |
| F-22 | (Key in the solution) keys imported and exported encrypted, under a key with two-person control | X — HSM |
| F-23 | (Key in the solution) audit of the key's generation, export, transport, revocation, expiry and deletion | X — HSM / operations |
| F-24 | (Key in the solution) the module physically protected under two-person control, its movements recorded | X — operations |
| F-25 | (Key in the solution) the movements of key backups recorded | X — operations |
| F-26 | (Key in the solution) the certificate request in PKCS#10 | X — the HSM or the CA's tooling (the Sandbox issues certificates directly) |
| F-27 | (Key in the solution) revocation asked at once when the key is compromised | X — operations, with the EC |
| F-28 | Current, unbroken algorithms | P (`rsa-1024`, `rsa-1024-cades`, `rsa-1024-xades`, `chain-sha1`, `alg-rsa-4096`, `alg-ecdsa-p256`, `alg-ecdsa-p384`) |
| F-29 | The application itself is signed with a code-signing certificate | X — the product's release (the NuGet packages are not what INDECOPI accredits) |
| F-30 | A viewer shows the signer and the recipient the document's integrity, signing time, public key and certificate data | P (`viewer`: the validation report; `simplesign validate --html-report --report-language es`). The product's own screen is X |
| F-31 | Signing time and the chain's public keys attached and signed (PAdES/XAdES/CAdES from the EPES-equivalent level comply) | P (`tsa-ok`, `pades-blt`, `pades-blta`, `cades-blt`, `cades-blta`, `xades-blt`, `xades-blta`, `cades-attached-blta`, `xades-detached-blta`, `xades-enveloping-blta`) |
| F-32 | Administrator and user manuals (security policies, configuration options) | X — the product's documentation (`docs/articles/iofe.md` documents the library part) |

## 4.3 Verification by automated agents (V)

Items 1–29 repeat those of 4.2 for a system that checks every signature it receives (and notifies the sender of the
invalid ones); differences are noted.

| # | What the guide asks | How |
|---|---|---|
| V-1 | Trusted list: INDECOPI's signature and chain | P (`v-tsl-ok`, `v-tsl-wrong-signer`) + U (`IofeRealListTests`) |
| V-2 | Trusted list: not expired | P (`v-tsl-expired`: TLNotExpired of `IofePolicies.Validation`) |
| V-3 | Trusted list: the signer's root is listed | P (`v-tsl-ok`, `v-tsl-tsa-unspecified`, `v-untrusted`) |
| V-4 | Trusted list: downloaded again periodically | U (as F-4) |
| V-5 | Revocation: CRL over HTTP, LDAP or HTTPS | P (`v-revoked`) + U |
| V-6 | Revocation: CRL signed by the CA entitled to | P (`v-crl-wrong-key`) |
| V-7 | Revocation: CRL current | P (`v-crl-expired`) |
| V-8 | Revocation: the CRL checked (the guide's text says "before signing", copied from 4.2) | P (`v-revoked`) |
| V-9 | Revocation: every certificate of the chain | P (`v-revoked`) |
| V-10 | Revocation: or OCSP for the certificate and its chain | P (`v-revoked`: the Sandbox answers OCSP too, which the validator asks first) |
| V-11 | The certificate and its chain have not expired | P (`v-expired`) |
| V-12 | The certificate's nonRepudiation bit | P (`v-no-nonrepudiation` with `IofePolicies.ValidationNonRepudiation`) |
| V-13 | Protected against unauthorized access | X — as F-13 |
| V-14 | The checks cannot be switched off | X — as F-14 (`ValidationPolicy`) |
| V-15 | Audit log | P (`audit`, `audit-refused`: signing; a verifying product logs its validation reports itself — X) |
| V-16 | Administrator rights cannot act outside the defined transaction | X |
| V-17 | (If the system signs the documents received) key only inside the certified module | X — as F-17 |
| V-18 … V-27 | Key copies, module certification and key custody, as F-18 … F-27 (when the system signs) | X — as F-18 … F-27 |
| V-28 | Current, unbroken algorithms | P (`rsa-1024`, `chain-sha1`) + U (validation of obsolete algorithms, `ValidationPolicy` Cryptographic constraints) |
| V-29 | The application is code-signed | X — as F-29 |
| V-30 | (If the system signs the documents received) a viewer for the relying parties, or a standard format INDECOPI approved | P (`viewer`, `v-altered`, `v-cades-altered`, `v-xades-altered`) |
| V-31 | (If the system signs) the validation data of F-31 (the body also asks a reference to the chain's non-revocation) | P (`pades-blt`, `pades-blta`, `cades-blt`, `cades-blta`, `xades-blt`, `xades-blta`: B-LT and B-LTA embed the revocation data) |
| V-32 | Manuals | X — as F-32 |

## 4.4 Time-stamps (S)

Requests to a TSA following RFC 3161; optional, for any of the three types.

| # | What the guide asks | How |
|---|---|---|
| S-1 | The token carries the identifier of the certificate of the TSA asked | P (`tsa-ok`, `tsa-unexpected`, `tsa-untrusted`, `tsl-tsa-unspecified`, `tsl-tsa-unlisted`) |
| S-2 | The token's signature verifies | P (`tsa-ok`, `tsa-invalid-token`) |
| S-3 | The TSA certificate is not revoked | P (`tsa-ok`, `tsa-revoked`, `tsa-revoked-cades`, `tsa-revoked-xades`) |
| S-4 | The TSA certificate has not expired | P (`tsa-ok`, `tsa-expired`, `tsa-expired-cades`, `tsa-expired-xades`) |

INDECOPI's list gives no TSA URLs: the TSAs it lists (Camerfirma, Acepta, Llama.pe, BPO Advisors, Girasol/FirmEasy)
are anchors, and the product configures each TSA's address with its provider (`docs/articles/iofe.md`).

## 4.1 End-user signing software (E)

For a product of this type the same steps apply; its items map to those of 4.2.

| # | What the guide asks | How |
|---|---|---|
| E-1 … E-4 | Trusted list block | = F-1 … F-4 |
| E-5 … E-7 | CRL over HTTP/LDAP/HTTPS, signed by its CA, current | = F-5 … F-7 |
| E-8 | CRL checked before signing, for the whole chain | = F-8, F-9 |
| E-9 | Or OCSP | = F-10 |
| E-10 | Certificate and chain not expired | = F-11 |
| E-11 | nonRepudiation and/or digitalSignature | = F-12 with `IofePolicies.Signing` (`no-key-usage`, `signed-no-nonrepudiation`) |
| E-12 | Web applications: a signature made in the browser is checked again on the server (certificate valid, signed data as sent) | X — the product's server, which validates what it receives with SimpleSign's validators (`PdfSignatureValidator`, `CadesSignatureValidator`, `XadesSignatureValidator`); the Agent signs only data `DataToSignInspector` accepts |
| E-13, E-14 | Key operations only in the subscriber's module; no automatic copies | X — as F-17, F-18 |
| E-15 | No obsolete algorithms | = F-28 |
| E-16 | The application is code-signed | X — as F-29 |
| E-17 | Viewer | = F-30 |
| E-18 | Validation data | = F-31 |
| E-19 | Manuals (and a programmer's manual for a library) | X — as F-32; SimpleSign's `docs/` and XML docs are the library's programmer's manual |

## Outside the annex: the process

| What | How |
|---|---|
| Evidence for every item (screenshots in annex B) | The TestBench's Playbook tab keeps each step's request, response, report and logs, and exports them (`docs/articles/playbook.md`) |
| A live audit session and a presentation to INDECOPI's commission | X — the applicant |
| A yearly follow-up audit in production | X — the operator; `IofeTrustedListSource.Changed` and the audit trail give the records |
| Security settings announced to the users (section 5) | X — the product |

Nothing here is **N**: every item a library can show has a step or a test; the rest belongs to the accredited product.
