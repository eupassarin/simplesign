How digital signatures work

Six short chapters, from the hash to ICP-Brasil, with something to try in each one.

Chapter 1

A fingerprint, then a seal

A hash (here SHA-256) turns any content into a short fingerprint. Change one letter and the fingerprint changes completely.

A digital signature is that fingerprint sealed with a private key that only the signer has. Anyone can check the seal with the matching public key, which travels inside the certificate.

SHA-256

The key pair (ECDSA P-256) was created in your browser just now. Sign, then edit the text: the signature stops matching.

In SimpleSign every hash and signature uses System.Security.Cryptography, the same cryptography .NET itself uses.

Chapter 2

How a PDF carries a signature

A signed PDF is the original file plus an incremental update appended to the end. The update adds a signature field whose value has two key parts.

Because the signed bytes are fixed, any later change to them breaks the signature. New signatures and LTV data are added as further updates, after the signed range.

Chapter 3

Inside the signature: CMS

The /Contents holds a CMS SignedData (the same format as a .p7s file). PAdES and CAdES add rules on top of it.

The signature covers the attributes, and the attributes cover the document through messageDigest. That is why a tampered PDF fails the integrity check even though the signature value itself still verifies. You can see this with the inspector and the “tampered” sample.

Chapter 4

Time and the long term: B-B to B-LTA

Certificates expire and keys get old. The PAdES baseline levels (ETSI EN 319 142) add evidence so a signature can still be checked years later.

Chapter 5

        
Trust: who vouches for the signer

        
A valid seal only proves that some key signed. To know who, the validator follows the certificate chain up to a root it trusts, such as the AC Raiz ICP-Brasil, and asks OCSP or CRL whether a certificate was revoked.

Chapter 6

        
Where the private key lives

        
The signature is the same in every case; what changes is where the private key is and who touches it.

        

          
            
A1: a .pfx file

            
The key is in a password-protected file. Easy for servers and automation; protect the file and the password.

          
          
            
A3: token or smartcard

            
The key cannot be copied out of the device. SimpleSign talks to its PKCS#11 driver; the device signs the hash.

          
          
            
Cloud certificate

            
The key lives in the provider's HSM (BirdID, VIDaaS…). The holder approves in the app or browser; only the hash is sent.

          
          
            
Deferred signing

            
Your server prepares the PDF, the user's device signs, and the server finishes. The key never reaches the server.
